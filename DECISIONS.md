# Architectural Decisions

A log of key technical decisions made in this project and the reasoning behind them.

---

## 1. Playwright over Cypress

Playwright supports true multi-browser testing (Chromium, Firefox, WebKit) from a single configuration, including mobile viewports. It also provides a unified API for E2E, API, component, and visual regression testing without additional plugins. The built-in `request` context allows HTTP-level testing without spinning up a browser, and `test.extend()` enables proper dependency injection through custom fixtures.

---

## 2. Page Object Model with lazy-evaluated locators

Page objects expose locators as `private readonly` properties using `this.page.locator()` rather than resolving them at construction time. Locators in Playwright are lazy — they are only evaluated when an action or assertion is called. This means no stale element references and no need to re-query the DOM manually between interactions.

---

## 3. Custom fixtures over global helpers

Instead of importing shared utilities in every test file, fixtures are composed via `test.extend()` and injected as test parameters. This approach mirrors dependency injection patterns from production code, makes dependencies explicit, and keeps test files focused on behavior rather than setup.

---

## 4. Separate CT configuration (`playwright-ct.config.ts`)

Component tests use a different Playwright runner (`@playwright/experimental-ct-react`) that mounts components in isolation without a running dev server. Mixing E2E and component test configurations in a single file is not supported — they require separate entry points and bundler configuration.

---

## 5. Visual snapshots excluded from version control

Screenshot baselines generated by `toHaveScreenshot()` are OS and GPU-dependent. The same component renders with subtle pixel differences between macOS and Linux. Committing snapshots generated on one OS causes visual tests to fail on CI running a different OS. Baselines are generated fresh in each environment via `--update-snapshots`.

---

## 6. `retries: 2` on CI, `retries: 1` locally

On CI, infrastructure flakiness (network latency, cold container startup) can cause legitimate test failures unrelated to code. Two retries on CI reduces false negatives without masking real bugs. Locally, one retry is enough to catch genuinely flaky tests during development.

---

## 7. `workers: '50%'` locally, `workers: 1` on CI

Running tests in parallel locally speeds up feedback loops without overloading the machine. On CI, a single worker ensures predictable resource usage in containerized environments where CPU allocation is limited and shared.

---

## 8. Planned: multi-user context isolation test

A future test will demonstrate BrowserContext isolation by simulating two
simultaneous users. User A adds a product to favourites in their context —
User B in a separate context sees no favourites, proving that localStorage
is fully isolated between BrowserContexts.

This showcases one of Playwright's key advantages: cheap, fast context
creation that provides complete browser state isolation without restarting
the browser.

---

## 9. Known issue: response time test skipped for external API

The response time assertion for the DummyJSON categories endpoint is
intentionally skipped. External API latency depends on network conditions,
server load, and geographic location — all outside this project's control.
The test is preserved in the codebase as documentation of the intent, but
marked with `test.skip()` to prevent flaky CI runs.

Response time testing belongs in dedicated performance testing suites
(e.g. k6, JMeter) targeting APIs under the team's control.
